# Database schema

PostgreSQL is the system of record. SQLAlchemy 2.0 models describe the tables, and Alembic owns schema changes. No product tables exist yet. Do not call `Base.metadata.create_all()` at application startup.

## Current state

`app/models` exports `Base` and does not define tables. `alembic/versions` is empty. The configured database can be created locally, but the application does not require it to start or to pass the current tests.

## Conventions for future tables

- Use plural snake_case table names, such as `profiles` or `job_postings`.
- Use `snake_case` column names.
- Give every table a primary key named `id`. Prefer UUID primary keys for records that will be exposed in the API.
- Store timestamps in UTC with timezone-aware `DateTime` columns named `created_at` and `updated_at`.
- Let the database enforce required fields with `nullable=False` and explicit foreign keys.
- Add indexes for columns used in lookups and joins. Name them `ix_<table>_<column>`.
- Name foreign-key constraints `fk_<table>_<column>_<referred_table>`.
- Keep one model class per table in `app/models`. Import the module from `app/models/__init__.py` so Alembic can see it.

## Migrations

Change schema only through Alembic:

```powershell
python -m alembic revision --autogenerate -m "add profiles table"
python -m alembic upgrade head
```

Review every autogenerated file before committing it. Autogenerate misses some renames and can drop columns that were only renamed in Python. Write data migrations by hand when a change is not a simple table edit.

`alembic/env.py` reads `DATABASE_URL` from application settings and points Alembic at `Base.metadata`.

## Access pattern

Routes do not receive the engine. They depend on `get_db()`, which yields a session and closes it after the request, rolling back if the request raises. Repositories accept that session and contain the queries. Services call repositories and commit at the service boundary once a use case succeeds.

## Planned areas, not yet modeled

These areas will get tables later, on their feature branches:

- Personal Knowledge Base and CV source data (`feature/profile-kb`)
- Job postings, requirements, matches, and generated application answers (`feature/job-intelligence`)

Agree on shared names and foreign keys before both branches add tables that reference each other. Until then, each branch should avoid inventing overlapping tables for the same concept.
